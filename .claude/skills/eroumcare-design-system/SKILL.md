# 이로움케어 반응형 디자인시스템

`CLAUDE.md`(이로움케어 반응형 정책 통합 문서)를 화면 제작/검수 작업에 바로 쓸 수 있게 패키징한 스킬입니다. 이 스킬은 **규칙 요약본**이며, 최신 원본과 화면별 결정 이력(왜 이 값인지, 언제 확정됐는지)은 항상 `CLAUDE.md`를 우선합니다. 이 프로젝트 밖(실제 개발 리포)에서 쓸 때는 아래 규칙만으로도 충분히 동작하도록 자기완결적으로 작성했습니다.

## 1. 브레이크포인트 (모든 컴포넌트가 이 값을 인용)

- **1024px** — PC ↔ 모바일 전환, 유일한 1차 분기. **1024px 이하 = 모바일, 1025px 이상 = PC**(정확히 1024px·아이패드 가로도 모바일). CSS: 모바일 `max-width:1024px`, PC `min-width:1024.02px`
- **360px** — 모바일 최소 지원폭. 콘텐츠 분기에는 쓰지 않음(모달도 360 분기 없음, 3-3)
- **앱별 사이드바 숨김(PC 안 2차 기준)**: 사업소 **1199px 이하** SNB 숨김 / 대대여(창고·설치파트너) **1439px 이하** SideNav 숨김 → 햄버거로 콘텐츠 위 오버레이, 콘텐츠·GNB 최소 폭 1440 유지 + 가로 스크롤
- 이 외의 값(480·640·768 등)은 브레이크포인트로 쓰지 않는다. 768 태블릿 프레임은 모바일 레이아웃 예시일 뿐
- **PC 콘텐츠 폭(브레이크포인트 아님)**: 이로움케어(소비자·사업소) **1060px** 고정 / 대대여 **1136px**(컨테이너 1200 − 패딩 32×2). 상한이 없으면 초광폭 모니터에서 무한정 늘어난다
- 폭 기준이지 입력장치 기준이 아니다 — 터치 노트북·가로 태블릿도 1025 이상이면 PC 레이아웃. hover 전용 동작은 만들지 않고 클릭으로도 100% 동작하게

## 2. 반응형 vs 적응형 — 화면 만들기 전에 먼저 판단

| 구분 | 정의 | 적용 |
|---|---|---|
| 반응형 | 같은 DOM을 CSS로 재배치, 화면 하나로 전 구간 대응 | 상세(3-11), 모달(3-3), 카드 목록형(3-10), 월간 캘린더 |
| 적응형 | PC/모바일 구조가 다름(테이블 vs 카드). **두 구조를 한 페이지에 두고** 1024/1025px에서 표시만 전환 | 테이블 리스트(3-9)와 검색 영역(3-7) |

- 판단 기준: 정보 밀도·조작 방식이 PC/모바일에서 본질적으로 다르면 적응형, 배치만 바꿔도 되면 반응형
- **어느 쪽이든 한 페이지(한 URL)** — 별도 모바일 페이지·앱 금지. **목록**은 모바일 전용 구조(카드)를 PC 테이블과 함께 넣고 표시 전환, **상세**는 PC 구조 하나를 반응형으로. 테이블을 CSS만으로 카드처럼 바꾸지 않음. 대대여 모바일(현재 별도 React 앱)·퍼블 `*_mobile.html`은 이 방식으로 합칠 대상

## 3. 컴포넌트별 반응형 규칙

### 3-0. 용어와 크기 기준 (PC / 모바일)
- **1024px 이하에서 크기가 바뀌는 건 입력칸·셀렉트·옵션 행뿐** — Textfield·SelectField 40/14px → **48/16px**, SelectOption 36 → **44**/16px. 공통 미디어쿼리 하나, 페이지 예외 없음
- 그대로인 것: 버튼 SM 36 / MD 48(LG 54는 하단 고정·바텀시트 하단만), 체크박스·라디오 20(모바일은 줄 전체 터치, 줄 높이 44↑), 토글 48×24, 필터칩 XL 40·SM 32, 선택칩 XL 44·SM 32, 탭 Underline 56·Outlined 48·Round 40 — 기기가 아니라 **쓰는 자리**로 고름
- 모달: 폭만 바뀜(`min(크기, 100% - 40px)`), 버튼 높이 48·폭 150 고정(좁으면 줄어듦, PC·모바일 같음)
- 입력칸 표시: 비활성(쓸 수 없음)·읽기전용(버튼으로 채움) 둘 다 bg `#eee`, 필수 = 라벨 뒤 빨간 `*`, 도움말 = 필요할 때만 입력칸 아래 한 줄, 에러 = 테두리 2px `#e53935` + 빨간 문구
- 용어: 3-1 **읽기 전용 정보 표**, 3-2 **입력 폼 배치와 입력칸**, 3-3 **안내·확인 모달**(DS Textfield와 혼동 금지)

### 3-1. 읽기 전용 정보 표
label-value 나열형 데이터(주문 정보, 회수 신청 정보 등).
- 라벨 셀: `max-width:128px; min-width:80px`, 배경 `#f5f5f5`
- 값 셀: `min-width:160px`
- **flex-shrink만 사용, wrap 없음** — 최소 240px(80+160)까지 좌우 2열 유지, 별도 스택 폴백 불필요
- 배경 없는 variant(예: 회수정보 조회형)는 라벨 125px, 배경 없음

### 3-2. 입력 폼 배치와 입력칸
배송정보 수정, 회수지 주소 수정 등.
- 라벨: **125px 고정, `flex-shrink:0`**
- 콘텐츠: `flex:1 0 0`, 최소폭은 모드에 따라 다름
  - 수정 모드: `min-width:280px` → 줄바꿈 전환점 = 125+gap(4)+280 = **409px**
  - 조회 모드: `min-width:180px` → 전환점 = 125+gap(8)+180 = **313px**
- 이 전환점은 브레이크포인트로 못박은 값이 아니라 공식에서 나오는 결과 — 라벨 폭/최소폭이 바뀌면 전환점도 바뀐다. **문서에는 숫자가 아니라 공식을 남길 것.**
- flex-wrap 컨테이너라 미디어쿼리 없이 순수 flexbox로 동작
- PC(1025px 이상) 상한: 입력 콘텐츠 영역은 `max-width:480px`에서 멈춤
- **반응형이어도 1024px 이하는 컴포넌트 MO 변형 크기로**: Textfield·SelectField 높이 **48**/패딩 12/**16px**(PC 40/8·12/14px), SelectOption 옵션 행 **44**/패딩 10·8·10·12/16px(PC 36/14px), TextArea 16px. 같은 DOM 재배치라고 PC 크기(40·14px)를 그대로 두지 않는다. **모달 안 입력류도 예외 없음**(미디어쿼리 하나로 페이지·모달·시트 전부 MO) — 디자인은 PC 모달 하나 + "모바일은 MO 크기 자동" 메모로 관리
- **입력칸 상태**(DS `Textfield`, 높이 PC 40 / 모바일 48, radius 4): 기본 1px PC `#616161`·모바일 `#bdbdbd` / 값 입력 1px `#333` / **포커스 2px `#323da3`** / 에러 2px `#e53935` / 비활성·읽기전용 1px `#bdbdbd` + bg `#eee`. 버튼으로만 채우는 칸(우편번호·기본주소)은 읽기전용 스타일
- **입력칸 안 정렬**: 글자·아이콘은 세로 가운데(`display:flex; align-items:center`). 크기는 높이(PC 40 / MO 48)로, 위아래 패딩 없이 좌우 12만
- **지우기(X) 버튼**: 텍스트 입력칸은 미입력 시 X 없음, 입력값이 있으면 X 노출. 읽기전용·비활성·날짜·셀렉트 칸은 X 없음. 누르면 값만 지우고 포커스 유지. 아이콘 24, 모바일 터치 40×40, 입력칸 오른쪽 패딩을 X 폭만큼 확보
  - 예외: **검색 칸은 X를 두지 않음** — 오른쪽 돋보기는 검색 실행 버튼이라 오른쪽 고정(Leading Icon으로 옮기지 않음) → 다시 누르면 글자 전체 선택. `type="search"`의 브라우저 기본 ×는 CSS로 숨김
- **입력 값별 키보드**: 숫자(휴대폰·우편번호) `inputmode="tel"`/`"numeric"`, 검색 `enterkeyhint="search"`(키보드만 닫음), 여러 칸 폼은 엔터 = 다음 칸("next"·마지막 "done"), 긴 글은 줄바꿈 + 글자 수 표시, 날짜·셀렉트는 키보드 대신 달력·옵션 시트. 모바일 입력 글자 **16px 이상**(작으면 iOS 확대)

### 3-3. 모달
**타입 판단 기준은 테이블(행/열 데이터) 포함 여부 — 요소 개수가 아님.**

| 유형 | 크기 | 모바일(1024↓) 형태 |
|---|---|---|
| 텍스트형(안내/확인) | **480** | 모달 |
| 정보확인/입력형/검색형 | **480** | **글자 입력이 있으면 바텀시트**(주소·사유·검색), 선택만 하는 팝업은 모달 |
| 테이블 포함형 | **600 / 800** | 모달(테이블 가로 스크롤) |

- **모달 폭은 한 줄**: 모든 모달 `width:min(모달 크기, 100% - 40px)` — 넉넉하면 원래 크기, 화면이 모달보다 좁으면 좌우 마진 20 남기고 Full. 크기를 바꾸는 미디어쿼리 없음, 340이라는 별도 크기 없음(예: 768 → 480/600/728, 390 → 350, 360 → 320)
- 바텀시트 폼은 입력 48 / 버튼 54
- **팝업 형태**: 모달(가운데, 짧은 안내·확인·선택, PC는 전부 모달) / 바텀시트(아래에서, 모바일 글자 입력·긴 선택지) / 옵션 시트(시트 안 셀렉트를 누르면 원래 시트 대신 열림, 선택완료 시 복귀) / 전체 화면(시트 최대 높이를 넘는 긴 폼은 새 화면)
- **모바일 결정: 입력 영역이 있으면 바텀시트** — 안내·확인 = 모달, 선택만 = 모달(길면 시트), 글자 입력(텍스트·숫자·검색·주소·사유) = 바텀시트, 테이블 = 모달. 예: 회수 요청하기 = 모달, 회수지 주소 수정·회수접수 취소·상품 변경 = 바텀시트. **예외**: 다른 팝업 위에 겹쳐 여는 짧은 입력(요양정보조회 위 '공인인증서 비밀번호', 4-5)은 모바일에서도 모달
- **검색 선택**(상품 변경 등)은 시트를 바꾸지 않고 한 시트 안에서: 입력칸 아래 결과 패널(OptionGroup, 테두리 `#333`, 행 SelectOption MO 44, 누르는 순간 틴트, 품절 회색·선택 불가)이 입력하는 대로 자동 표시(돋보기·"검색" 키는 키보드 닫기) → 결과를 누르면 입력칸에 값 + 패널·키보드 닫힘 + 확인 버튼 활성. 검색어를 고치면 선택 해제. 결과 없으면 "검색 결과가 없습니다"
- **버튼 높이**: 모달 버튼 MD 48(PC·모바일 같음), 바텀시트 하단만 LG 54
- **버튼 폭**: 모든 모달 버튼 **각 150px 고정 + gap 12px, 가운데 정렬**(PC·모바일 같음). 모달 안쪽이 좁으면 버튼이 줄어든다(`flex:0 1 150px`). 바텀시트 하단 버튼만 **Full**(LG 54). 버튼명이 150에 안 들어가면: 버튼 1개는 글자만큼 늘어남(패딩 20, 최대 모달 안쪽=Full), 버튼 2개는 버튼명을 짧게(약 6자).
- 정중앙 정렬, 오버레이는 하나만(새로 열리면 기존 것 자동 닫힘), 내용 넘치면 모달 자체 `max-height` + 내부 스크롤.

### 3-4. 액션 버튼 배치
- **PC**: 페이지 타이틀 옆(우측), Hug 사이즈(`flex:0 0 auto`) — 전체폭 분할 금지
- **버튼 크기는 PC 그대로**(SM 36 / MD 48, PC·모바일 같은 값, 미디어쿼리 없음). 예외는 하단 고정·바텀시트 하단 버튼 **LG 54**. 입력칸 옆 버튼(우편번호)은 36 + 입력칸 높이 가운데 정렬. 폭에 따라 바뀌는 건 입력류뿐
- **모바일**: 타이틀 아래로 이동 + 화면 하단 sticky 플로팅(흰색 그라데이션 페이드), 버튼은 폭을 나눠 가짐(Full)
  - **예외 — 주문요청관리 상세(4-3 대여·4-5 구입)의 주문취소/주문하기는 모바일에서 타이틀 아래 한 줄, 폭을 나눠 가짐, MD 48**(하단 고정 아님, 2026-10-07). 회수 상세 등 다른 상세는 공통 규칙 그대로
- 모바일 하단 sticky는 `env(safe-area-inset-bottom)` 필수
- 모바일 하단 고정 버튼 영역 여백: **위 32 / 좌우 20 / 아래 20 + safe-area** (`padding:32px 20px calc(20px + env(safe-area-inset-bottom))`, `viewport-fit=cover`) — 화면 하단 sticky 버튼에만 적용, 바텀시트·검색 시트 하단 버튼은 기존 그대로(위/아래 32). 페이지 버튼만 20인 이유: 뒤 본문을 상시 가리므로 높이를 줄임.
- 모바일 본문 맨 아래 일반 버튼(주문목록 등, 고정 아님): 영역 여백 위 48 / 아래 20 아래 여백 0이면 안드로이드·인앱 브라우저에서 툴바에 붙음

### 3-5. 팝오버 / 바텀시트
- **PC**: 트리거 아래 4px·왼쪽 정렬 팝오버. **정보 팝오버**(타이틀 + 닫기, 예: 도서산간비)는 **클릭**으로 열고 X·바깥 클릭·ESC로 닫음. **짧은 아이콘 안내**만 호버 200ms 열림 / 300ms 닫힘(클릭으로도 동작)
- **모바일**: 탭하면 바텀시트(하단 "확인" LG 54)
- **PC 팝오버 그릇**: 340, 패딩 24/20, radius 16, 테두리 1px `#bdbdbd`, 그림자 `0 8px 24px rgba(0,0,0,.2), 0 0 4px rgba(0,0,0,.12)`
- **안의 구성(타이틀 + 리스트형, PC·MO 같음)**: 타이틀 줄 32(20px Bold 왼쪽 + 닫기 32 오른쪽, 세로 가운데) → 간격 PC 12 / MO 16 → 리스트 박스(`#f5f5f5`, radius 4, 패딩 8/12, 행 32: 이름 왼쪽 16px `#555` / 값 오른쪽 16px Bold, 보조 설명 14px `#999`) → ※ 안내(위아래 8, 14px `#555`)
- 달력/셀렉트 드롭다운도 동일 원칙: 모바일은 트리거와 동일한 좌우 여백(`left:0;right:0`), PC만 고정폭

## 5. 코드 레벨 원칙 (반복 발생한 실수에서 도출 — 새 화면 만들 때 기본 적용)

1. **모든 input/select/커스텀 필드는 배경·글자색을 명시적으로 지정한다.** 미지정 시 OS 다크모드에 따라 브라우저가 임의 렌더링(실제 버그: select 검은 배경).
2. **아이콘은 이모지가 아니라 인라인 SVG.** 텍스트 화살표(▾▲▼)나 `☰`/`✕` 같은 기호도 SVG로. `<select>` 기본 화살표도 `appearance:none`+`background-image`로 커스텀 SVG 지정(우측 인셋은 보통 12px, 다른 입력요소 좌측 패딩과 대칭).
3. **하단 고정 요소는 `env(safe-area-inset-bottom)` + viewport 메타 `viewport-fit=cover`.** 기본 아래 여백은 3-4.
4. **오버레이는 항상 하나만** — 새로 열리면 기존 것 먼저 닫기.
5. **화면을 복제하면 숨김 레이어·문구·옵션을 다시 확인.** 정상 버튼 hidden + 범용 버튼 노출, 다른 화면의 문구·셀렉트 옵션·시트가 남는 사고가 반복됨(주문 화면에 반품 검색 시트, 셀렉트에 지역 샘플).
6. **폰트는 SUIT, 사이즈는 14px 이상 짝수(14/16/18/20/22...)만.** SUIT는 `https://cdn.jsdelivr.net/gh/sunn-us/SUIT@2/fonts/static/woff2/SUIT.css`로 로드, `font-family` 최우선 지정. 예외: Figma가 명시적으로 작은 값을 지정한 배지류(예: 원형 숫자 배지 9px)만 유지 가능 — 임의로 홀수/13px 이하로 조정 금지.
7. **크기·위치는 JS로 px을 박지 말고 CSS 비율로.** 로드 때만 계산한 px은 창 크기·회전 때 어긋남(구입/대여 토글 사례). JS가 필요하면 resize 때 재계산.
8. **입력칸 안 아이콘(돋보기·달력·지우기) 폭만큼 오른쪽 패딩** — 입력 글자가 아이콘 밑으로 들어가지 않게.
9. **한 페이지 원칙** — 모바일을 별도 페이지로 만들지 않고 PC 페이지 안에서 1024px 이하 전환.

## 6. 화면 제작/검수 워크플로우 (Figma MCP 활용 시 — 반드시 지킬 것)

**숫자를 추측하지 말고 항상 Figma에서 실측한다.** 라벨 폭·gap·min-width 같은 값은 감으로 쓰지 말고 `get_metadata`(구조 파악) → `get_design_context`(실제 스타일/컴포넌트 바인딩)로 직접 확인한다.

**컴포넌트 variant 개수를 판단할 때 반드시 마스터 컴포넌트를 확인한다.** `get_design_context`는 **그 화면에 실제로 쓰인 variant만** property 타입에 나열한다 — "이 화면에 6개 상태만 보인다"를 "컴포넌트에 6개 variant만 있다"로 오판하지 말 것. 실제로 이 프로젝트에서 이 실수를 한 적이 있다(Status chip-Rental이 9개 variant를 전부 갖고 있었는데, 화면에 6개만 쓰여서 "3개가 없다"고 잘못 진단함). 컴포넌트의 진짜 전체 variant 목록을 보려면:
- `search_design_system`(entity: "component")으로 컴포넌트 검색 후 라이브러리 파일에서 마스터 컴포넌트 노드를 직접 `get_metadata`로 열어 모든 `Property 1=...` symbol을 확인, 또는
- 디자인시스템 캔버스(컴포넌트 모음 페이지)에서 같은 이름의 컴포넌트 프레임을 찾아 대조

**인스턴스인지 raw 도형인지 구분한다.** `get_design_context` 결과가 `<ComponentName property1="..." />` 형태로 함수 호출처럼 추상화되면 진짜 컴포넌트 인스턴스, 매번 인라인으로 markup이 풀어써지면 raw 도형(컴포넌트 아님)일 가능성이 높다. 같은 컬럼/영역 안에서 어떤 셀은 인스턴스, 어떤 셀은 raw로 섞여 있으면 디자인시스템 검수에서 반드시 지적할 것 — 색상이 우연히 같아도 유지보수 시 갱신이 안 되는 문제로 이어진다.

**같은 라벨이라도 도메인이 다르면 다른 컴포넌트다.** 예: "배송완료"가 `Status chip-Order`(구매)와 `Status chip-Rental`(대여) 양쪽에 있을 수 있다 — 화면의 실제 도메인에 맞는 컴포넌트를 쓰고 있는지 확인.

**새 프로토타입/화면 파일을 만들 때는 기존 harness 패턴을 그대로 따른다**(이 리포 기준, 다른 코드베이스에서도 참고):
- SUIT 폰트 `<link>` + `font-family` 최우선 지정
- `@container pf (max-width:1024px)` / `(min-width:1024.02px)` 형태로 1024/1025px 경계 분기 (미디어쿼리 아닌 컨테이너쿼리)
- 프리셋 폭 버튼(320/360/1024/1025/1440)으로 브레이크포인트 구간을 클릭 한 번에 확인 가능하게
- PC 콘텐츠 영역은 `max-width:1060px`로 캡핑
- 적응형(리스트) 화면은 `.pc-view`/`.mo-view` 같은 명시적 분기, 반응형(상세/모달) 화면은 단일 DOM 유지
